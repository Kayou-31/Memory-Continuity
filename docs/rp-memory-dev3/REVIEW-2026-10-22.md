### A1：完整分支事务容量

基线复现输入 4,166,534 UTF-8 字节，包含 256 个事件，每个带 61 个合法 span。实际写出的 transaction envelope 为 4,301,627 字节。commit 返回成功，随后 readFence 和冷启动 authorize 均返回 store_corrupt。这里是单个分支事务 envelope 的写读不一致，与 dev.3 已实现的全局累计状态 3/4 MiB 限制是不同路径。

修复在统一 `#append` 使用已有 `checkedRpJson` 检查**最终** envelope，并写入同一个编码字符串。派生 payload 在内存中形成草案，容量和元数据重放校验通过后才写 blob；因此容量拒绝不增加事务或派生 blob。有效小批次仍能用原键重试。没有截断事务、删除证据、放宽读取器或修复已经损坏的历史。超限新写入返回已有的 `capacity_exceeded`。

### A2：旧宿主 packet 的摘要证明缺口

复现先采纳只依赖 source 的摘要并发送 packet，随后从该 source 建立事件并 retcon，原 source 按设计保留。存储里的有效摘要数量已为 0，新生成 packet 也不含该摘要，但下一次实际 SDK 请求同时带上旧 runtime context：旧摘要 sentinel 再次到达合成 terminal。终端共收到 2 次请求，最后请求中的旧上下文为 obsolete=true，新上下文为 false。

建议给 packet 类快照记录实际注入的 summary/state 等 record ID、revision、内容哈希，在每次认证时校验这些依赖。对无法认证的旧 packet 历史明确采用拒绝/干净续接规则，不能事后用新状态认证旧文本，也不能通过删除原始 source 来掩盖问题。这涉及快照 schema 和恢复规则，本次 store 内部重构没有顺带变更它。

### A3：失败发布的明文遗留

分别在 blob rename、commit rename 前注入 EIO；同输入重试发布成功后，再执行 `privateDeletion(...publicationDisposition: 'delete')`。删除返回成功，已登记 publication 不可读，但递归检查独立合成 profile 仍找到第一轮的 `.txt.tmp-*` 或孤立 `.txt` 正文。这是物理删除覆盖范围缺口，并非已证明旧正文还能通过正常检索 API 读取。

建议记录可信的操作草案与待发布路径，或在持有 scope writer lock 且完整验证历史后回收确属本次失败操作的孤立文件。必须保留独立且明确 retain 的 publication，不能按正文哈希粗暴删除其他发布副本。全局 control 有 purgeStatus，但本轮有效复现没有取得该状态；结论只依赖删除返回值和磁盘明文扫描。

### A4–A8：恢复与宿主边界

- A4 已实测 canonical accept 的缺 seal 重试。`summarizer` 的 adopt/reject、`jobs.enqueue`、`savePayloadCopy` 也有类似快捷返回点，属于静态待核范围，没有宣称逐条实测。建议统一“核验已提交效果、补齐 seal、再确认成功”的入口，保留幂等键冲突语义。
- A5 对照使用同一原生 adapter，唯一差别是 tool-call 前是否输出 text。纯工具路径 terminal 调用 2 次且 ready=true；混合消息调用 1 次且 ready=false。应逐 block 验证允许的 text 与工具调用、维护精确请求证明，同时继续拒绝未认证 reasoning/rich content，不能一律放行全部块。
- A6 应在命令边界将 JSON 语法/结构错误转为 invalid_record，不进入持久化故障封锁分支；I/O 和认证错误仍 fail-closed。
- A7 应先写入授权草案并完成持久化，再将 grant 激活到可复用内存集合；失败时撤销临时句柄，重试不能绕过保存。
- A8 需要明确区分未绑定和已绑定健康状态，或采用显式生命周期状态枚举。错误的 status 不能作为实际准入测试的唯一判据。

## 已实施的算法优化

### 同次验证加载内复用固定历史前缀

原 `#historical` 每遇到父分支，都从最初事务重新播放；嵌套 fork 会递归重复同一前缀。现在使用绑定到具体 WorkspaceState 的 WeakMap，按 branchId/revision 保存已重建状态，并记录该状态来自第几笔事务。只有缓存来源 sequence 不大于当前重放前缀长度时才命中，避免借用“未来”状态。写缓存和命中返回都克隆，避免分支修改污染缓存。

缓存仅在同一次已验证 load 及其历史前缀内共享。其他请求、authority、后续磁盘读取都不会复用它。校验和、磁盘身份、最新隐私 tombstone、可见性及读取前后 fence 校验继续执行。缓存增加一次加载期间的内存占用，换取减少重复重放；尚未测量大 payload、多千分支的峰值内存。

另将事务幂等键查重从每笔扫描所有前序 transactions，改为该次加载内部的 Set。该子步骤由累计 O(T²) 比较变成期望 O(T)，不代表整个存储读取变成线性，也没有单独测出它的墙钟收益。

### 实测

通过实际 store API 建立嵌套的空分支，在真实 `#apply` 入口只插入计数，不替换行为。每个规模读取一次；没有真实模型、额外并行测试或低内存限额。原始 JSON 为 `replay-baseline.json` 与 `replay-optimized.json`。

| fork 深度 | 事务数 | 原重放次数 | 新重放次数 | 原读取耗时 ms | 新读取耗时 ms |
|---:|---:|---:|---:|---:|---:|
| 4 | 5 | 62 | 30 | 7.07 | 6.48 |
| 8 | 9 | 1,022 | 90 | 16.81 | 10.00 |
| 12 | 13 | 16,382 | 182 | 132.45 | 13.95 |

深度 12 的计数减少约 90 倍，该次耗时减少约 9.5 倍。计数反映了这类嵌套分支的重复工作消除；耗时只是**一次小型合成微基准**，不是 p95、统计显著性或所有长剧情的性能保证。回归测试约束操作次数，不用依赖机器负载的时间阈值。缓存未引入持久化 checkpoint，不宣称解决所有全量重放成本。

### 派生正文草案与发布

commit 先收集正文编码和哈希，支持同批后一个事件读取前一个事件草案进行 supersedes 校验。统一 append 在最终闭包构造完成后做容量预检，再写正文，最后重新 authorize，才发布事务。只读复审发现延迟写正文曾使最后权限检查提前，已用真实 blob_published 故障钩子改变 workspace marker nonce 先红后绿修复。复审已确认最终检查恢复到正文写完之后。

新回归文件 `test/rp-replay.test.mjs` 有 5 项：

1. 12 层 fork 的实际重放次数受多项式上界约束；基线 16,382 次失败，修复后通过。
2. 完整事务超限在写任何新派生 blob 前拒绝；旧 fence、磁盘文件集合、冷启动读取保持可用，缩小批次后可提交。
3. 同批 supersedes 可以读取已准备的前一事件，最终只保留纠正后的事件。
4. 写正文过程中 workspace marker 身份改变，提交返回 scope_denied 且不增加事务。
5. 固定父修订不吸收后续独立来源；下一次读取对磁盘篡改仍返回 store_corrupt。

## Ultra 与“完整人生”的后续方向

审查期间用户明确目标：希望 Ultra 的长项目记忆、检索和上下文优化与 RP Memory 配合，让 AI 角色能够持续经历一段完整人生。这里需要的是跨章节、跨续接的身份和因果连续性：过去经历会影响此后的关系、目标、承诺和行为。不是将全部旧聊天反复放进上下文就算实现。

当前已验证的共存包是 Ultra `0.6.1-dev.rp.1`。其 `src/index.ts` 与 `src/memory-host.ts` 明确通过 `engineeringAllowed` 排除 RP 会话：工程记忆捕获、检索、注入和压缩在 RP 中停用。因此现状是可同时安装且相互隔离，不能宣称两套记忆能力已经叠加。源码静态依据包括 Ultra `index.ts:155,169,192,207,317,382,390,401` 与 `memory-host.ts:133,205,230,243,254`。这些文件在 `work/host-followup/ultra/package/src/`，本轮没有修改。

建议保持 RP 为剧情记忆的唯一事实管理者，通过适配层复用 Ultra 的预算分配、按需检索、长期任务组织等方法，避免双重写入和两套摘要互相冲突：

| 需要持续保留的内容 | 在体验中的作用 | 设计约束 |
|---|---|---|
| 原始经历与时间线 | 记得何时、与谁、因为什么发生某件事 | 原始证据可追溯，纠正不伪造旧经历 |
| 当前事实与角色认知 | 知道现在的处境，也能表达误会、怀疑和后来澄清 | 世界事实和角色相信的内容不能混为一谈；未来若做视角过滤需单独验收，本轮 strict POV 仍关闭 |
| 关系及其变化原因 | 相识、信任、冲突、修复具有前因后果 | 方向明确、有支持事件，不能只存一个无依据好感分数 |
| 长期目标与未完承诺 | 多章之后仍能继续正在做的事情 | 承诺/目标有提出、改变、完成、放弃的记录；推测不能直接写成既成事实 |
| 章节与人生阶段摘要 | 上下文有限时保留主线并按需回看细节 | 摘要是可失效的派生材料；retcon/删除后所有旧注入也必须复验 |
| 当下相关的回忆 | 不必每次全想起，但遇到相关人物/地点/目标能找回往事 | 在授权、分支、有效性过滤之后排序；具体权重必须用标注场景评测 |

可实现的循环是“发生经历 → 形成有来源的事件 → 更新状态/关系/未完事项 → 产生可检查的阶段摘要 → 当前场景触发相关回忆 → 支持下一步行为”。技术上应让 Ultra 的通用算法读取 RP 提供的有界、已认证视图，并把建议作为候选交回 RP；不能让工程压缩直接改写 RP 宿主历史、绕过 owner 或自动把建议采纳为剧情。

还有一个与成长直接相关的语义设计空缺：普通候选采纳目前生成 `fictionalTime: null`、`supersedes: []`（`summarizer.ts:101`），reducer 对没有明确替代关系的不同状态/关系值保留 conflict（`reducer.ts:31,51`）。因此，“小时候不信任某人，后来被其救助而信任增加”不能仅靠追加两个值，就假定已经支持正确的当前关系演化。后续需要有来源、因果与顺序校验的**正常状态迁移**，与误会澄清、叙事 retcon 分开；不能按最后写入时间强行覆盖。这里是静态确认的现有语义边界，没有额外计为第九项已复现缺陷，也未在本轮改变其保守冲突规则。

实现顺序建议：先修 A2/A3 等完整性问题，再建立批量授权视图；随后用一个固定、多阶段人生故事测试人物身份、关系因果、长期承诺、纠正后行为和干净续接；最后才评估更主动的整理与行动能力。评测既要检查“记得什么”，也要检查“为什么这么记、哪些应当不知道、下一次选择是否遵循有效经历”。真实长期人格/行为连续性尚未验证，本轮没有增加自主代理、生产自动摘要、压缩或自动采纳。
