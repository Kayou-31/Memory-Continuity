## 本轮确认并修复的问题

**P2：公开核心的通用人物提交入口漏查实体白名单。** 人物草稿只允许配置中的 `entityIds`，但 `canonical.applyControl` 对带 `personProtocol` 的事件只验证结构，允许可信调用者通过原始 `accept` 提交未知人物的起点和初始字段。这样创建的对象与 `person.read` 的白名单规则不一致。这是独立核心 API 的契约漏洞，不能扩大描述为模型工具、管理 HTTP 或远程提权。

- `src/rp/canonical.ts`：人物起点的 actor 和人物字段的 subject 同样检查已配置实体；普通旧 v1 事件的含义与底层存储格式不变。
- `test/rp-person.test.mjs`：新增 `raw canonical person protocols cannot introduce entities outside the configured registry`，覆盖未知起点实体、已知起点配未知字段实体、拒绝后分支不变以及正常人物仍可创建。
- 真实失败证据：修复前返回 `ok:true`，预期为拒绝，退出码 1；修复后人物整文件 5/5，退出码 0。见 `evidence/release-0.2-preview/regression/`。
- `SOURCE-MANIFEST.json`：随实际源码重新构建生成；最终发布包必须包含本修复，不能复用修复前的安装包。

## 历史异常的重新裁定

此前一次完整测试为 212/213，4097 条记录的冷读出现 `Cannot use 'in' operator to search for 'value' in [object Unknown]`。本轮检查 `schema.ts` 的对象描述符校验、分段重建和全局加载路径，未找到修改描述符内建函数的测试代码；此前 20 次读取、其后的完整测试和本轮新增完整验证均未复现。**根因仍未确定，未修改校验来掩盖错误，也不归因为硬件、磁盘或 V8。**

已观察到的行为是拒绝读取，现有证据没有显示损坏数据被接受或写入。本项作为预览版已知稳定性风险公开保留；不据此承诺生产稳定性。若再次出现，应保留原始工作区、日志和备份，停止依赖该存储的写入并调查。

## 保留的边界

- 全历史校验的成本随历史增长；检索游标尚无容量淘汰，长期运行和大规模吞吐没有验收。
- 在线隐私删除不清理独立备份、宿主日志或已经交付浏览器的文本；未引用分段页不自动回收。
- 关闭后撤销新请求资格；已发送给文件系统的重命名或已发送的网络内容不能事后撤回。同进程恶意代码不属于能力隔离保证。
- 分段布局的普通发布／控制硬上限为 8／12 MiB；硬上限可能拒绝新的控制事务。默认布局仍为 3／4 MiB，不截断事务及幂等历史。
- 较早浏览器已完成创建／编辑／成长／关系／承诺等操作；最终长 ID 换行与清空选择器的浏览器复查受内置标签页崩溃阻断，仍未验证。
- 真实模型长期理解、多日使用、真实断电、生产配置迁移、其他操作系统／Node 版本及任意 Ultra 组合未验证。
- 完整用途产品、技能学习、多人物社会、自主生活、分支持久检索索引和更长历史管理界面仍未完成。
