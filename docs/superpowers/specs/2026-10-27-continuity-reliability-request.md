## 三、第一阶段：修复正确性和调用链问题

### 1. 工具预算预检与实际请求保持一致

重点检查：

- src/rp/rp-plugin.ts
- src/rp/context-retention.ts
- src/rp/token-budget.ts
- 对应成本与注入宿主测试

已有线索：

toolSizing 在保留并计入当前 packet 后，又把 lastContextBody 作为下一份上下文预留计入。在上下文复用路径中，可能重复计算同一份完整上下文。

这里的问题是预检双算，不应未经验证就描述为实际重复发送或重复收费。

目标：

- 工具结果预检、组装阶段和最终发送采用一致的请求内容定义。
- 复用当前包时只计算一次。
- 换包时计算退役后的历史与新包。
- 保留真实包装、工具声明、历史和必要余量。
- 明确区分 UTF-8 字节、保守计量单位、本地 tokenizer token 和供应商 usage。

验收：

- 当前必要上下文占预算约六成时，小型状态查询或检索仍能正常执行。
- 连续工具步骤不会因虚构的第二份上下文被拒绝。
- 实际超预算仍被正确阻止。
- 上下文复用、换包、多工具步骤、冷恢复均有相关回归。
- 不能通过删除必要上下文让测试通过。

### 2. 修复全局授权撤销的时间窗口

重点检查：

- src/rp/global.ts
- 全局发布、读取及撤销相关测试

已有线索：

- 发布最后一次 approval 检查之后，还有异步写入，再提交事务。
- 读取最后一次 authority 检查之后，还有异步加载，再返回正文。
- scope fence 不变时，单靠版本比较可能发现不了 authority 被撤销。

目标：

- 明确定义撤销与提交的生效边界。
- 撤销已经生效、且操作尚未跨过提交边界时，不得继续发布。
- 受保护读取在释放结果前，必须确认当前授权仍然有效。
- 已提交或结果不确定的操作继续保持正确的幂等和恢复语义。
- 将通用检查集中复用，避免多个接口各自遗漏。

验收：

在排队、正文写入、事务发布前、最后一次元数据读取等确定性位置触发撤销，验证实际结果。

分别覆盖“内容被撤回”和“读取权限被撤销”，不能只测其中一种。

核心 API 的复现与上层宿主、HTTP 接口的验证应分别报告，不扩大结论。

### 3. 打通长资料的授权检索

重点检查：

- src/rp/person/documents/
- src/rp/retrieval.ts
- src/rp/retrieval-index.ts
- src/rp/injection.ts

已有线索：

文档块可以大于后续可选记忆预算。默认关联深度下，超预算块可能被整体排除；普通检索又有意排除文档控制来源与 manifest，因此出现“资料完整保存，但模型需要时无法取用”。

目标：

- 保留完整原文及其权限边界。
- 保存分块与模型读取片段可以采用不同粒度。
- 大块放不下时，仍能选取相关原文片段，或提供简短索引及按需展开入口。
- 为文档提供与现有受众、人物、场景及平台条件一致的检索和分页读取路径。
- 检索结果必须带可验证的来源范围。
- 原文更新、更正、撤回或权限变化后，旧索引、游标与片段必须正确失效。

不能直接解除普通 retrieval 对 user_control 或文档 manifest 的过滤，也不能把整个文档改为 mandatory 绕过预算。

验收：

- 一份明显超过后续可选预算的已授权文档，仍能找到并读取其中指定内容。
- 验证命中在开头、中间、末尾的情况。
- 验证中文、Unicode、分页与修订。
- 验证私聊、群聊及其他受众条件不会被新检索路径绕过。
- 未匹配、无权限、已失效和预算不足应有可区分的结果。

目标：

验收：

- 批量读取中发生更正、撤销、删除时，不得返回混合版本或越权结果。
- 性能结果标注环境、样本规模和测量范围，不编造通用加速比例。
