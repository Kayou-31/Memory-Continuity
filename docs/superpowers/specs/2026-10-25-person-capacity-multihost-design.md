# Memory-Continuity：完整人物资料、32K 注入与多宿主设计

日期：2026-10-25。状态：用户已确认，进入串行实施；不是已发布功能。

代码基线：`1d997516a3cb0621163a94a2bb16b1a7bd28243c`，Memory-Continuity 0.2.1。
调查与实际诊断见 [RESULTS](../../framework-evolution-2026-10-25/RESULTS.md)。

## 要解决什么

让人物可以保留完整的身份、语气、偏好、规则、经历和关系，而不必为了导入先把自己压缩成几句话；让同一个人物在 DSH 或独立 AstrBot 中延续，同时知道当前是在群聊、私聊还是特定关系中交流。

用户已确定：AstrBot 独立使用，共用记忆核心；纳入 NapCat 和 Snow Luma；注入预算是 **32,768 token**，仍受模型实际总预算约束。继续串行开发，不开启后台主动行为、自动摘要、自动采纳、上下文压缩，不接付费 API。随后补充明确授权：增加双方共同日记，AI 在显式启用后可自行通过专用工具写日记，用户可写、可读、可修订，修改 AI 日记的额外提醒可关闭。

这是下一轮开发设计。0.2.1 仍是当前正式版，不能提前把下文写入“已支持”列表。

## 路线选择

已讨论的两条路线是：让 DSH 当大脑、AstrBot 负责收发；或者独立 AstrBot 插件，共用核心。用户选择了后者。

具体实现建议：保留 TypeScript 核心，提供独立 Node.js 入口及受认证的本机服务；AstrBot 用 Python 薄适配层连接它。这样沿用同一套存储、来源验证、纠错和撤销逻辑。把核心重写为 Python 会产生第二套事务和迁移实现，本轮不采用。

```text
Memory-Continuity TypeScript 核心
  ├─ DSH 适配入口（保留 rc.2、rc.3）
  ├─ 本机管理工作台（复用现有界面与人工确认流程）
  └─ 独立本机服务 ← AstrBot Python 插件
                         └─ AstrBot 的 OneBot v11 适配器
                              ├─ NapCat
                              └─ Snow Luma
```

“独立 AstrBot”意味着不安装、不启动 DSH，仍需要运行共用核心所用的 Node.js。独立核心发行物不应通过 peerDependencies 强制安装 DSH。NapCat 与 Snow Luma 首批通过标准 OneBot 接入，不分别维护重复的记忆插件，也不捆绑对方程序。

用户进一步确认按平台分包。同一源码仓库分别产出核心包、DSH 插件包、AstrBot 插件 ZIP 和完整源码；NapCat/Snow Luma 各有接入说明和验证记录。现有 DSH npm 包名先保留，核心与 AstrBot 独立声明运行要求，不把所有平台依赖塞进同一安装包。只通过 GitHub 分发本轮构建，不额外推断 npm 注册表发布授权。

服务在用户显式启用后按需运行，不注册系统开机任务，不启动轮询、定时整理或主动聊天。首批由用户显式启动本机核心服务；插件检测服务状态并给出诊断，不悄悄安装运行时或创建系统服务。部署自动化可另议。

## 1. 人物原文与可用记忆分开保存

现有 2048 UTF-16 单元字段、64 KiB 草稿入口继续按 v1 语义读取。新功能使用独立的资料文档能力，不能直接把旧字段限制改大，写出旧版能够打开却不能正确读取的数据。

新增人物资料文档：

- 原文、来源名称、原始字节哈希及导入版本完整保留；支持 UTF-8 文本、Markdown 和明确版本的 JSON。首批不执行附件中的脚本、不解析带执行能力的格式。
- 建议首批单文档上限为 **1 MiB UTF-8**；正文分块存储并保留原文顺序及定位。分块是存储方式，不删字、不自动生成摘要。超过上限明确拒绝，允许用户自行拆为多个文档。
- 工作台预览标题、分类、正文差异、重复项和未识别段落，再显式确认。未知段落保留在“待分类”，不能静默丢弃。命令传递短期导入凭据，不要求粘贴巨大 JSON，也不接受模型指定的任意本机文件路径。
- 原文归档不会自动成为已认可的记忆或有执行权的指令。用户分别决定哪些内容进入人物定义、规则、知识或经历；导入声明与事件事实保留不同来源和认知类型。
- 编辑、导出、重新导入保持内容、顺序和 Unicode 一致。发现冲突、损坏或过期预览时整批不发布；不能留下半个人物。

文件预算与完整持久化 envelope 预算同时校验。1 MiB 是文档入口上限，不是“无论现有存储多大都保证成功”。容量不足时保留旧数据，报告不足原因；不以截断历史换空间。未分段全局 v1 继续使用 3 MiB 普通发布、4 MiB 控制上限；已有显式分段布局继续使用 8 MiB 普通发布、12 MiB 控制逻辑 envelope 上限及其分页限制。两种布局均保持现行校验，不能自动迁移、扩限，也不能把已迁移的 profile 降回较小额度。

## 2. 分类和关系语境

吸收参考包的五个组织方向：**人物、规则、程序、记忆、知识**。它们是工作台的组织方式，不是五套各自写库的系统。

- 人物：身份、背景、性格、价值观、表达习惯；支持多条语气样例和自定义子分类。
- 规则：用户给人物的边界与行为偏好，保留现有系统硬约束和人物建议规则的区分。
- 程序：展示本项目已经实现的确定性约束与能力模块；本轮不提供可执行脚本或任意代码导入。
- 记忆：有来源的经历、关系、目标、承诺，复用现有审阅、撤回和纠错。
- 知识：可检索资料，标明来源、时间、版本和信任状态，不伪装成人物亲历。

新增条目级适用条件：通用、私聊、指定对象、指定群或其他显式场景。平台、机器人账号、会话类型、群 ID、发送者 ID 由宿主适配器提供；模型正文中的自称不构成身份或授权。

授权范围先过滤，再按场景与相关性选择。“更相关”“被置顶”都不能扩大可见范围。索引标题、命中数量和原因预览同样不得泄漏不可见条目。来源于私聊的关系和记忆默认不进入群聊；人物的公开身份可显式共享。

跨平台人物可以复用，同名账号不会自动合并。账号对应关系、群可见范围和私密资料共享都必须由本机管理员显式设置。未知映射默认无权限。

## 3. 32K token 的注入闭环

新增预算协议，明确 `unit: tokens`、默认上限 `32768`、计数方法及版本。现有预算协议和注入绑定仍按原来的保守字节语义处理，不能将历史数字静默解释成另一种单位。

32K 是**每次实际模型请求中的全部记忆内容总上限**，不是每一层分别 32K。人物核心、规则、语气样例、关系、往事、知识、全局记忆与必要包装，以及同轮记忆工具回填和请求中仍保留的旧记忆工具结果，合计受 32,768 token 约束。重复出现的内容按实际发送次数计数；其他非记忆工具的内容仍计入整次请求总预算。

记忆工具在返回前按剩余额度分页或减少条目，回执必须绑定实际返回内容，不得先认证完整结果再在宿主偷偷截断。历史中必须保留的内容已超预算时提示诊断或显式干净续接，不启动自动压缩，也不伪造精简后的旧回执。

每轮先按权限取同一版本的记录，再按条件挑选；为必须保留的身份和边界分配预算，然后分配可选语气样例、往事与知识。必需内容本身超限时明确拒绝，展示哪部分过大；不静默删掉边界或把超限隐藏在“必需”标记后面。

可用预算同时受以下约束：

1. 用户配置的记忆上限，默认 32,768 token。
2. 已核实的模型输入上限，扣除宿主提示、当前输入、历史、工具定义和其他请求内容。
3. 已核实的上下文上限，另扣回复及工具调用预留。

总预算必须基于实际完整请求重新校验，不假设所有模型都有 1M 上下文。流式请求、工具循环、重试和模型切换都要在发送前重新检查。

计数分两类，工作台明确展示：

- 有匹配的本地 tokenizer：绑定模型标识、tokenizer 名称和修订版，按实际将发送的文本计数。模型映射未知或发生变化时，不沿用旧计数。
- 没有可核实的 tokenizer：展示“保守估算”，继续使用保守的文本字节额度和现有请求保护，可能少用一部分 32K 额度。不能将字符比例估算宣传成精确计数。无法界定的多模态/服务端模板开销不能宣称已严格计量。

首批 tokenizer 的具体实现由开发者在能力调查后选定，并写出支持的精确模型名单；**不能用未知模型的近似 tokenizer 验收“32K 精确 token”**。如果找不到可离线验证的计数器，就记录精确计量阻塞，保留明确标记的降级方式，不能因此放宽准入校验。

保留五层注入与展开深度，扩展到条目级条件和文档定位。原因预览增加：适用对象、选择原因、实际展开范围、计数单位/方法、各层用量、总量、预算淘汰原因及当前快照版本。预览必须与发送内容一致。

## 4. 独立核心和跨进程权限

首批核心服务仅监听 loopback；请求采用强随机凭据，凭据不出现在普通日志或群聊里。管理工作台继续校验来源与会话、预览后确认。远程开放和公网管理不在本轮范围内。

服务端持有真实 HostAuthority，RPC 只传受限的短期会话句柄。客户端提供的 `owner`、`approved`、`scope` 等 JSON 字段不能换来权限。普通记忆工具保持有界只读；用户后续授权的专用日记写入是单独的受限能力，不授予人物编辑、事实采纳、纠错、删除、发布全局记忆或执行宿主命令的权限。管理员的预览与确认使用不同能力，不能用通用 `rp_exec` 作为模型工具。

同一 profile 使用明确的单写入者所有权。首批 DSH 的现有嵌入模式与独立服务不得同时写同一个 profile；检测后拒绝第二个所有者。跨宿主迁移先停旧所有者，再校验备份和重新绑定。实时双宿主共享写入必须后续改为同一个核心服务独占写入，本轮不承诺文件夹共享即实时同步。

跨进程准备、准入、取消和提交都要有版本凭据、超时和幂等键。校验与发送之间的撤权竞态必须通过可验证的准入生命周期处理，不能只依赖“刚刚查过一次”的 HTTP 结果。服务退出或连接中断后，旧会话句柄失效；已发送但结果不明的输入进入诊断状态，不自动重放。

资料缓存及检索索引只能来自通过校验的已接受快照。不能扫描 blob 目录把暂存、已撤销或已删除资料重新当作记忆。纠错、撤回、隐私删除要使文档片段、派生索引、预览和进行中的请求一起失效。

## 5. AstrBot、NapCat 和 Snow Luma

调查基线：AstrBot **v4.29.3**、NapCat **v4.18.41**、Snow Luma **v2.2.0**。这是拟验证的版本，不表示已完成兼容，也不代表参考包使用的版本。

AstrBot 插件提供：显式人物绑定、只读记忆工具、本轮临时记忆上下文、管理入口、状态诊断、停用和干净续接。通过 `on_llm_request` 修改请求只是其中一环；普通钩子异常会被宿主捕获，必须明确停止事件。工具循环还需要实际 provider 请求边界的保护，无法可靠实现就拒绝该组合，不能静默降级成不受保护的发送。

使用宿主支持的临时内容机制，使动态记忆不作为普通用户消息永久写入聊天历史；保存原始用户/助手内容时仍须区分事实、说法和提案。旧的未认证工具历史不直接迁入可信记忆。清空聊天不等于删除人物，删除人物资料也不能让旧聊天快照继续复活。

NapCat 与 Snow Luma 的首批范围：OneBot v11 私聊/群聊的文本消息、可信账号与会话标识、重复消息处理、断线重连后的幂等处理，以及由 AstrBot 正常触发的回复链路。图片、语音、主动消息、空间、头像更换和平台专属扩展均不在本轮。

同一机器人会话不能同时从两个传输端接入造成重复写入。消息 ID 要与机器人账号、持久化的接入实例标识和会话范围组合；这里的接入实例不是每次重连新生成的 socket ID。重连必须保留幂等命名空间，不能把同一输入记成第二次经历；切换传输端前停用旧连接并显式迁移绑定，不能默认两个端的 ID 可互换。平台通知或无法验证的撤回事件不能伪造成普通聊天证据。

Snow Luma 以用户自行安装的独立组件通过公开协议连接，不复制其源码、专有组件或配置凭据。参考包中涉及的账号配置、人物隐私与历史资料均不进入仓库或发布包。

## 6. 双方共同日记（用户后续补充）

用户希望双方都能记录相处经历和感受，并读到彼此的日记。它不是只有管理员能写的日志，也不应变成模型可以改动所有可信记忆的后门。

- 一个可选“共同日记”能力，默认关闭；用户显式开启后，在当前对话内向 AI 提供日记说明、查询及专用写入工具。AI 可自行决定何时写，不逐篇请求人工审批，也不启动后台会话或定时任务。
- AI 通过受限工具创建自己的日记；可修订自己的既有日记，但保留原稿和版本链。用户通过工作台写自己的日记、读取双方内容，并可修订 AI 部分。AI 无权改写用户日记或切换用户的提醒偏好。
- 作者身份由宿主会话能力确定，不能信任模型传来的 `author` 字段。AI 写入绑定实际会话、输入/工具调用和幂等键；失去会话所有权或被关闭后立即撤权，结果不确定时诊断，不盲目重写。
- 每篇记录作者、创建与修改时间、正文、关联人物/人生分支、可见范围和修订依据。日记可以表达感受和主观看法，按“用户日记”或“AI 日记”标注，不能未经另行人工采纳就变成客观事实、关系结论或人物核心定义。
- 首批正文每篇最多 16 KiB UTF-8，标题最多256个Unicode码点；超限明确报错，不静默截断。日记可跨会话检索，进入相关性选择与同一32K记忆预算，保留来源和版本证明。此条限制只约束一篇日记，不收紧1MiB人物原文导入。
- 默认只对当前共同日记的参与者和绑定人物开放，不自动分享到群聊或其他人物。用户在工作台写入的日记由该人物在后续有权限的对话中读取；普通检索、摘要和原因预览同样遵守范围。
- 用户修改AI日记时，默认显示“这篇由 AI 写下；保存后将保留原稿并记录你的修订”的额外确认。可在工作台关闭此提醒；关闭后仍需用户明确点击保存，仍检查版本和权限，保留修订记录，不把人的改写冒充AI原话。
- 普通修订保留历史；用户明确进行隐私删除时，所有相关版本、派生索引和缓存依既有删除/清除流程失效或清除，不能拿“保留原稿”阻止删除。

这项用户新授权取代原方案“所有模型工具只读”在日记范围内的限制；自动采纳、后台自动行为和付费调用的禁令保持。

## 7. 数据迁移与兼容

保留 branch/global v1 的已有语义；新人物文档、受众条件和 token 预算按独立 requiredCapabilities 或明确协议版本引入，旧读取器不能忽略未知能力继续写入。

启用新能力前生成可验证备份；只在所有新记录和能力标记可持久化后发布。故障时原 profile 可诊断，恢复不靠删历史。旧人物不自动拆解、提炼或迁移；用户看过预览再确认。原文导入不需要真实模型。

参考包用于需求和静态审查，不执行其中的脚本，不把 AGENT 文本加载为开发指令，不导入私人数据库或凭据。新回归用合成中文、英文、emoji、长语气样例和私聊/群聊场景构造公开 fixture。

## 8. 串行交付顺序与验收

1. **人物容量、原文导入、分类、共同日记与 32K 预算**：先做失败回归，再改核心、工作台和 DSH 入口；测边界、完整往返、原子失败、旧读取器拒绝、群/私聊隔离、AI日记授权与作者版本、提醒开关、完整请求计数和预算显示。先在 DSH rc.2、rc.3 验证。
2. **独立核心发行物和本机服务**：脱离 DSH 启动、读写、冷启动恢复；测认证、撤权、跨进程单写入者、重复确认和不确定结果。
3. **AstrBot 独立插件**：实际 AstrBot 运行时配离线终端；验证首次请求、工具循环、重试、停用、断开核心、旧历史、临时内容不持久化和跨会话隔离。不以手写 mock 通过代替实际宿主证据。
4. **两种 OneBot 接入**：先做协议契约及断线/重复事件测试，再在具备可用宿主时做实际 NapCat/Snow Luma 验收。真实账号登录、发送消息或修改账号配置另需明确授权；当前授权覆盖接口调查与离线适配。
5. **报告、文档与打包**：一轮连续的 typecheck、build、完整测试、fixture、pack；AstrBot 的独立验证和两种 QQ 端证据分别列出。未实测部分保留，不混写为“全部兼容”。确定版本后再更新发布说明。

未来可做：多宿主同时使用同一个核心服务、更多平台、语音与多模态记忆、大型知识库、可选主动机制。它们不混入本轮验收。

## 实现前仍须通过的技术门槛
