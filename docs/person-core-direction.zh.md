2026-10-23，按用户最新产品方向补充。本文确定后续组织方式；未实现的部分不计入本轮已交付功能。

完整设计提案见 [人物核心与自有分支设计方案](superpowers/specs/2026-10-23-ultra-rp-person-core-design.md)，包含人物模型、编辑与确认流程、存储兼容、模块边界和分阶段验收；M0/M1 已验证并本地提交；M2 已实现字段成长与显式候选审阅，最终验收详见 RESULTS.md。M3 模块框架和 M4 长期体验评测仍是后续计划。

## 产品中心

**让用户自己搭建、持续塑造一个完整的“人”。** 用户可以决定这个人是谁、从哪里来、在意什么、怎样表达，与谁有什么关系，如何从经历中作出选择并发生变化。记忆、任务和工具围绕这个人物组织。

一次人物创建应逐步形成：身份与人生背景；性格、价值观、偏好和边界；表达习惯；重要关系及彼此知道的事情；人生阶段、愿望和长期承诺。用户应能查看每项设定来自初始定义还是后来的经历，也能明确锁定、修改、撤回和保留不同人生分支。

后续互动要保持可解释的连续性：一次共同经历可以成为关系变化的原因，一次成功或失败可以成为认知和目标调整的依据。临时情绪、他人的说法、主观信念和确认的事实应有不同含义；重大人格变化应有明确原因与用户控制，避免每轮对话重新塑造人物。

## 主插件与能力分支

Ultra-RP-Memory 自成体系，可以发展多条功能与用途分支；主包继续独立可用。分支可以落成可选模块或独立产品变体，共用人物记忆底层。物理仓库、子包与 Git 分支的组织方式在实现时再确定，本轮没有移动或合并其他插件仓库。

**Ultra-Mode 是独立的平行项目，通过兼容层配合。** 它不需要被收编为 Ultra-RP-Memory 的子模块，也不是启动人物核心的前提。双方维持共享会话准入、明确的权限边界与上下文预算；可以保留可关闭的纯排序适配，不以复用其全部工程能力为前提。

| 组成 | 职责 | 当前状态 |
|---|---|---|
| Ultra RP Memory 人物主体 | 人物档案、人生经历、关系、当前认知、愿望/承诺、成长因果与回溯 | 已有原子创建、离线草稿、宿主绑定、字段编辑/策略、显式成长队列、时间线，复用定向关系和目标账本 |
| 自有项目助手分支 | 项目经验、计划进展、项目检索和上下文安排 | 完整用途分支尚未实现；已有可选 Ultra 兼容适配，与分支本身分开 |
| 技能与工具能力 | 编程、研究、创作等实际行动及可验证结果 | 后续可选模块；本轮未新增执行工具或技能学习 |
| 生活与互动能力 | 日常偏好、表达、互动方式与可选择的生活场景 | 后续可选模块；本轮未开启自主生活或后台任务 |

RP、陪伴、创作、项目助手等用途可以各自发展交互与能力组合。它们共用人物定义、来源、关系、成长和回溯规则，具体用途不应被写死为所有人物的统一行为。

能力模块应有明确的启用状态、权限、来源和生命周期。一个模块的故障或关闭不应抹掉人物主体；卸载模块后，已由用户确认的人生经历仍可由主插件独立解释。

能力结果进入人物记忆时，应提供原始来源、实际结果状态、关联人物/项目/会话、适用分支和可验证证据，由主插件决定是否形成候选，再经用户确认采纳。模块不得直接改写身份、价值观、关系或其他分支；失败、未完成、推测和确认结果需要保留区别。工具使用能力不自动意味着这些经历已经成为人物事实。

## 下一阶段顺序

1. **人物创建与编辑。** 提供可填写、可预览的人物档案，先覆盖身份、背景、表达、偏好与边界；明确初始设定、锁定设定和可成长部分。
2. **人格与人生连续性。** 为价值观、性格、信念、人生阶段定义有来源的状态模型与变更规则；支持查看变化理由和保留矛盾待用户处理。既有状态 JSON 不会被静默迁移成新语义。
3. **自有分支与能力接口。** 为 RP、陪伴、创作、项目助手等用途提供可选能力组合，实现有权限和来源的结果回传、独立启停与故障隔离；Ultra-Mode 在外部兼容层保持独立，不强制成为内部模块。
4. **面向人物的评测。** 验证长期身份、关系、选择依据与经历回忆；分别记录规则正确性、真实模型表现和长期运行成本。现有 fixture 与本轮 260 阶段持久化测试不能代替这些评测。

本轮实现仍保持显式采纳、独立 npm 包和既有 fail-closed 协议；离线人物界面和显式字段成长已落地；完整实时人物界面、技能学习、能力模块注册/生命周期框架仍属于后续阶段。
